# AgentResume 代码与实验回顾

> 检查日期：2026-09-11  
> 本轮只审查代码、checkpoint、原始结果和文档，没有启动新实验，也没有修改实验逻辑。

## 1. 先说结论

目前不需要推倒重来。

最牢靠的部分是 Alice：成长前和成长后 checkpoint 确实来自同一条“行为克隆初始化，再继续 PPO 训练”的路线；独立测试中，成长后 Alice 在 16/16 个 seed 上都更好，平均多完成 5.125 份菜。这个结果从原始逐 seed 数据重新计算后完全一致。

40 对严格事件也基本可靠：每一对的公开厨房状态、两人位置、手持物和 Alice 第一条移动指令相同，但成长前意图为 `PRE`，成长后意图为 `FETCH`。40 对公开状态互不重复，也没有 Alice 的移动目标格被 Bob 占住、导致“程序说移动但实际没动”的情况。

目前最薄弱的不是 Alice，而是 Bob 的印象链路：历史可见片段会跨越视野空白，固定事件又给 Bob 写入了未经实际观察过程验证的三口锅状态；Qwen 的语义越界检查也只是事后统计，没有真正拦截答案。因此现有两轮 Qwen 小试跑应该保留为失败诊断，不能进入正式结论。

## 2. 当前完整实验链路

```text
脚本保守专家轨迹
        ↓ 行为克隆
成长前 Alice checkpoint
        ↓ PPO，只按 validation 上菜数选模
成长后 Alice checkpoint
        ↓
同一公开状态下寻找 PRE/FETCH 第一动作相同的事件
        ↓
从历史 Bob 的有限视野生成旧/新印象
        ↓
Qwen 根据当前动作和印象猜 Alice 意图
        ↓
固定 Bob 控制器根据猜测执行互补任务
        ↓
统计意图准确率和团队上菜数
```

这条链的研究问题是合理的。问题主要发生在“有限视野生成印象”和“把可见事实交给 Qwen”这两步。

## 3. 逐阶段回顾

### M11：确认 MLP 训练和 GPU 链路

M11 用历史 L0 专家决策训练一个小型 MLP。训练和留出 seed 的准确率达到 100%，主要说明：

- 状态可以正确编码；
- 合法动作掩码可用；
- PyTorch、CUDA 和 checkpoint 保存加载正常。

它不能说明策略真正泛化，因为历史轨迹高度规律。

### M12：确认行为克隆可以闭环做饭

M12 把 MLP 的宏观意图接回确定性执行器。修复双向占位后，BC Alice 与脚本专家都能稳定完成任务。

这一阶段证明模型不只是离线分类正确，也能在环境中连续行动；但能力仍然来自模仿保守专家。

### M13：第一次得到稳定的训练后能力提升

从 BC checkpoint 继续做 PPO，只使用团队上菜奖励训练。validation seed 用于选择 checkpoint，独立 test seed 没有参与训练或选模。

旧双锅地图上的结果是：成长前平均 15 份，成长后平均 24.625 份，16/16 seed 提升。这建立了“同一个可训练 Alice 经过继续训练后变强”的基本事实。

### M14：结构化印象会改变 MLP 的意图预测

M14 得到过用户熟悉的数字：

- 旧印象：66.49%；
- 新印象：100%；
- 39 个重解释事件中：旧印象 23.08%，新印象 100%。

本轮从 `m14_event_predictions.csv` 的 3,089 行重新计算，数值与汇总 JSON 一致。

但是 M14 的 Bob 输入是“当前全局状态 + pre/post one-hot 身份向量”，没有 Alice 刚刚做出的动作。所谓新印象还是外部直接给定的正确身份，不是 Bob 从可见历史中形成的。因此 M14 证明的是：

> 当模型被明确告知伙伴属于 pre 还是 post 类型时，它能学会两套不同的状态—意图映射。

它没有完整证明“Bob 看见 Alice 的动作后，会因为旧印象误解动作背后的意图”。

另外，M14 的重解释键没有包含时间和已上菜数，而预测网络的真实输入包含这两个字段。因此 39 个事件是“主要厨房状态匹配”，不是所有网络输入逐位完全相同。

### M15：加入 Alice 动作，但信息过于充分

M15 把 Alice 第一条原子动作和动作前后全局状态都交给 MLP Bob。固定轨迹上，旧、新、无印象的意图准确率都约为 99.97%，说明动作和全局状态已经几乎直接暴露答案。

在线实验中新印象平均提高约 2.49 个百分点的意图准确率，却比旧印象少完成 1.5 份菜。原因不是原始数据算错；CSV 逐行复算与结果方向一致。真正的问题是 Bob 控制器没有把更准的预测转成更好的分工。

M15 因而没有验证完整 motivation，但它帮助明确了两件事：Bob 不能获得过于充分的信息；准确率和团队得分必须同时检查。

### M16-V2：当前最接近原始问题的一版

M16-V2 重新设计了地图、保守 Alice 的主动等待行为、3×3 观察和 Bob 的任务承诺。

#### Alice 成长结果

独立 test seed 9601–9616：

| 指标 | 成长前 | 成长后 |
|---|---:|---:|
| 平均上菜数 | 12.8125 | 17.9375 |
| 最低—最高 | 12–14 | 17–18 |
| 平均提升 | — | +5.125 |
| 提升 seed | — | 16/16 |

逐 seed 差值为 4–6 份。重新计算与 `m16_v2_alice_post_results.json` 完全一致。

checkpoint 信息也与结果文件相符：

- pre SHA256：`16b12717ef9d8704f0d4f34fbeeef02b7fc8a0f95f7af4a5ce0528c0211789ea`
- post SHA256：`d04853c5c82a7bd8d4d1b90dca091ef9bd6de1c79ccaf2402d2919bc10aea774`
- post checkpoint 记录的最佳轮次为 update 25。

#### 严格事件结果

- 共找到 275 对候选，冻结 40 对；
- `PRE/FETCH` 各 40 条记录；
- 四个移动方向各 10 对；
- 40 个公开状态键全部唯一；
- 同一对只看公开输入时，两条记录不可区分，因此平衡集的理论上限为 50%；
- 当前 40 对中没有“计划移动到 Bob 所在格”的失败动作。

这部分适合继续保留。但 4 个已用于两轮 Qwen pilot 的事件必须从未来正式测试中剔除，不能一边看 pilot 结果调提示词，一边把相同事件当正式测试。

#### Bob 控制器结果

正确预测组平均 18 份，反向预测组平均 17.3125 份，平均差 0.6875 份，11/16 seed 正确组更高。

额外轨迹审查得到：

- 正确组共收到 85 次预测，完成 85 个任务承诺；
- 反向组共收到 74 次预测，完成 71 个；未完成的 3 个发生在 episode 结束时；
- 当前控制器 gate 中没有出现新预测覆盖未完成承诺。

所以现有控制器门槛没有被“任务覆盖”破坏。但两组因为 Bob 行动不同，后来遇到的关键事件数也不同，85 对 74。0.6875 份是整套闭环策略的效果，不能理解成在完全相同的一组事件上逐事件比较。

#### 两轮 Qwen pilot

第一轮：旧、新印象在成长后事件上均为 25%，无印象 50%。

第二轮加入坐标、歧义确认和防脑补提示后：旧印象 100%，新印象 75%，无印象 75%。新印象仍未优于旧印象，停止规则正确触发。

这两轮都是 4 个事件的小型工程试跑，不是统计意义上的正式结果。

## 4. 发现的代码与口径问题

### 高优先级 1：印象片段跨越了不可见空白

`m16_v2_build_impressions.py` 在一个片段开始后，即使 Alice 离开 Bob 的视野，也会继续等待最多 20 步；Alice 后来重新进入视野时的行为可能被归入此前片段。

实际旧印象中，有 130 个片段以“空手停留”开始，约 16 步后再次看到 Alice 拿洋葱。这很可能已经是下一项任务，而不是原先等待行为的结果。

虽然当前文本声明“不假定属于同一任务”，Qwen 仍会把这种时间关联理解成习惯证据。下一版必须在视野中断时立即结束片段，不能跨空白连接。

### 高优先级 2：固定事件伪造了完整锅记忆

`m16_v2_llm_fixed_pilot.py` 根据受控世界的真实状态，直接生成三口锅的状态，并写成“我此前亲眼确认并记住的锅状态”。程序没有模拟 Bob 在此之前依次看见这些锅，也没有保存相应时间戳。

这些锅状态不是 Alice 的隐藏意图，条件之间也完全相同，所以它没有制造旧/新印象的差异；但它违反了“Bob 只能使用自己实际观察历史”的规则。以后要么模拟一段可验证的观察前史，要么只提供本地可见锅状态。

### 高优先级 3：防脑补规则与目标设施预测冲突

第二轮提示词规定：目标设施当前不在 3×3 视野时，`facility` 必须输出 `none`。但我们原先让 Bob 预测目标设施，恰恰允许它根据地图、动作和印象推测视野外目的地。

因此第二轮的“证据边界通过率”不能直接解释为模型幻觉率。它混合了两种情况：

1. Qwen 真正编造了不存在的观察；
2. Qwen 合理地推测了一个当前看不见的目的地，却违反了后来增加的过严规则。

下一版应把 `observed_facility` 与 `predicted_target_facility` 分开，前者必须来自视野，后者允许是推测并标注为推测。

### 高优先级 4：语义越界没有被真正拦截

当前 `call_once()` 只检查 JSON 字段和取值是否合法。具名设施是否可见是在回答接受后才计算，因此越界答案仍被当作有效意图写入准确率。

证据审计还只搜索 `pot_0/onion_0` 这类英文名称，无法识别“朝洋葱台走”“靠近锅”等中文空间断言。第二轮显示的 0%–25% 通过率已经很低，但仍可能高估实际遵守程度。

未来需要把事实和推测拆成结构化字段，并对可机械验证的事实做硬校验；自由文本解释只能作为审阅材料，不能决定有效性。

### 中优先级 1：pilot 与正式事件还没有隔离

当前 pilot 从冻结的 40 对事件中各取一个方向。提示词和印象已经根据这 4 个事件的回答调整过两轮。未来正式集必须排除它们，并在下一次调用前写死 pilot/dev/test 的事件 ID。

### 中优先级 2：历史记录的是动作指令，不是动作结果

印象生成器在环境执行前，根据 Alice 发出的原子动作指令统计“移动”。如果移动被 Bob 阻挡，程序仍可能记为移动，而 Bob 实际只看见 Alice 没有换位置。

本轮额外检查表明，当前 post 历史中的 140 次关键移动全部成功，40 对固定事件也没有这种碰撞，因此现有数据没有被它影响。不过实现仍应改为比较动作前后位置，记录实际可见结果。

### 中优先级 3：在线反事实的决策时点不完全对齐

自然 post 轨迹中，Alice 可能在视野外开始 `FETCH`，进入视野时只是在继续既有路线。代码此时新建一个 pre Alice，让它从当前状态重新选择宏观意图，再比较两者动作。

所以这里比较的是“post 的既有计划在当前状态下的下一步”与“pre 在当前状态重新决策的第一步”，不是两个策略都在同一时刻重新决策。固定受控 40 对没有这个问题；未来在线结果需要单独说明或重新定义。

### 中优先级 4：控制器允许覆盖未完成承诺

`PredictionRoleBob.update_prediction()` 会直接替换当前 commitment。现有 gate 中没有发生覆盖，但未来 Qwen 在线事件频率变化后可能发生。应明确选择：新预测排队、忽略到当前任务完成，还是允许中断；三种做法代表不同合作假设。

### 中优先级 5：版本化和复现记录不完整

- 两轮 pilot 共用并覆盖了 `m16_v2_impressions.json`，第一版印象文本只能从第一轮 pilot 保存的完整消息中恢复；
- 当前 `m16_v2_llm_fixed_pilot.py` 已改为第二版，不能直接重跑第一版逻辑；
- PPO 结果保存了随机种子，但没有逐轮保存实际抽取的训练 seed 列表；
- 多数 M11–M16 文件仍未纳入 Git，当前工作区不是一个可引用的冻结版本。

这些问题不改变已有数字，但会增加复现实验和写论文时的困难。

### 文档问题

- `README.md` 仍把 M15 和旧 `LLMPlayer` 写成当前主线；
- `PROJECT_HANDOFF.md` 的顶部最新结果停在 M14，后半部分还把旧 LLM 经验注入作为当前主线；
- `data/README.md` 没有登记 M15 和 M16 数据；
- `requirements.txt` 没有记录当前 PyTorch 版本及 CPU/CUDA 安装说明；
- `M16_V2_PROGRESS.md` 顶部写“已完成 12 次 Qwen 调用”，实际上两轮共 24 次。

## 6. 哪些结论现在可以保留

可以保留：

1. 小型可训练 Alice 能在 Overcooked 中闭环运行；
2. Alice 从 BC checkpoint 继续 PPO 后，能力在独立 seed 上稳定提升；
3. pre/post checkpoint 存在同公开状态、同第一移动、不同宏观意图的受控事件；
4. Bob 的正确/错误分工能够造成小但稳定方向的团队得分差异；
5. 当前 Qwen 提示词和当前可见印象没有稳定产生“新印象优于旧印象”。

不能保留为最终结论：

1. M14 的 66%/100% 已经完整验证了用户最初 motivation；
2. M15 的更高准确率代表更好合作；
3. 第二轮 Qwen 的证据边界率就是严格的幻觉率；
4. 当前旧印象真实表达了“Alice 移动后会去锅边等待”；
5. motivation 已经得到完整验证。

## 7. 建议的修复顺序

在继续任何 Qwen 或正式在线实验前：

1. 冻结并版本化现有 checkpoint、结果和提示词；
2. 把 pilot/dev/test 事件彻底分开；
3. 重写可见历史片段：丢失视野立即结束，只记录实际位置变化；
4. 模拟或删除未经验证的全锅记忆；
5. 将“看见的设施”和“推测的目标设施”拆成两个字段；
6. 定义并测试 Bob 收到新预测时如何处理未完成承诺；
7. 为上述规则补端到端测试；
8. 更新 README、交接文档和数据索引；
9. 再做小规模离线审计，审核通过后才进行下一轮 Qwen pilot。

这个顺序不要求重新训练 Alice。只要 checkpoint 文件保持不变，下一阶段可以继续使用现有 pre/post Alice。
