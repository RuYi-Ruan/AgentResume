# M19 扩展方案：在 M17 基线上做多 seed × 多地图 + 提示词稳健性的复现

> 前置：`docs/experiments/M18_FINAL_ANALYSIS.md`（M18 确认性实验未复现，A 协议弃答失效、D/B 阴性）。
> 目标：把 M17 的"单地图、单组 checkpoint、80 事件"的正向结论，扩成**可复现包**：多个 Alice 训练 seed × 多张地图 + 提示词稳健性；结论只在通过门槛后采信，途中结果差就调整或重来。

## 0. 侦察结论（已实测）

- M17 的事件构造脚本 `scripts/m17_prepare_fixed_events.py` **已经参数化了 checkpoint**（`--pre-checkpoint/--post-checkpoint`），但布局硬编码为 `AMBIGUOUS_KITCHEN_V2`。
- 把布局 monkeypatch 成 M18 的 map A、checkpoint 换成 M18 `group_1`（训练 seed 1802）后：
  - `load_policy_checkpoint` 正常，pre/post 的 `ObservationSpec` 完全一致；
  - 候选事件枚举跑通，**得到 165 个合法配对事件**（pre 意图 PRE、post 意图 FETCH、首步动作相同、后续公开状态一致）；
  - 运行需要 conda 环境 `agentresume`（torch 2.1.0+cpu），仓库 `.venv` 里没有 torch。
- M18 已有 **9 组训练好的 Alice（3 seed × 地图 A/B/C）**，能力门槛全部通过（pre≈14、post≈20 碗 / 700 tick），可直接作为 M19 的 checkpoint 池。

也就是说：**M19 不需要重新训练任何模型，只需要把 M17 的流程参数化并重跑推理/Qwen。**

## 1. 实验设计

| 项 | 设定 |
|---|---|
| Alice 来源 | M18 artifacts：`artifacts/m18/v1_waitfix_20260915/checkpoints/group_{0..8}/{pre,post}.pt` |
| 覆盖 | 先做 **6 组**：地图 A/C 各 2 seed + 地图 B 2 seed（若容量不足按实际数量接受）；通过后再补满 9 组 |
| 配对事件 | 沿用 M17 规则：同局面、同首步动作、同后续公开状态，pre=PRE / post=FETCH，目标设施不同；每组目标 50 个（不足按实际，需留 audit 说明） |
| 印象 | 沿用 M17 的"只从可见历史片段"生成：每组各跑 40 个历史起点，pre 得旧印象、post 得新印象 |
| 条件 | 旧印象 / 新印象 / 无印象（主对照）；保留 oracle 作为 B 链上限参照 |
| 提示词 | **复用 M17 原始提示词（v1）为主**，额外加 2 个同义改写版本做稳健性（只改措辞，不改任务定义、事实表与真值） |
| 重复 | 每个 (事件, 条件) 跑 3 次投票（M17 当时 1 次即全员一致；3 次更稳，代价可接受） |
| 判分 | 事件级配对：意图准确率（PRE/FETCH）、设施准确率、**弃答率单列**；主检验新旧 McNemar + bootstrap 95% |

## 2. 执行步骤

### S0 参数化与单组试跑（半天）
1. 给 `m17_prepare_fixed_events.py`、`m17_build_paired_impressions.py`、`m17_fixed_online_rollout.py` 加 `--layout {A,B,C,v2}` 与 `--group/--pre-checkpoint/--post-checkpoint/--label` 参数（当前只有 checkpoint 参数）。
2. 复用 `configs/m18_v1.json` 的地图定义，别新造布局。
3. 用 `group_1`（map A）跑通全链路：候选枚举（已实测 165）→ 事件划分 20 dev / 50 formal → 历史印象（各 40 起点）→ 提示词构造（不调 API，audit 输出）。
4. 记录 dev 事件的 pre/post 意图分布、动作分布，确认与 M17 同构。

### S1 小 pilot（先验可答性，必须过门槛）
- 在 `group_1` 的 **12 个开发事件**上，用 M17 提示词跑 3 条件 ×3 重复（108 次调用，约 20 分钟）。
- **通过门槛（缺一不可）**：
  1. 弃答率 < 30%（M18 的 77–98% 是失败形态）；
  2. 新印象 − 旧印象 ≥ +20pp（方向 + 幅度）；
  3. 无印象介于两者之间或接近新印象（M17 的形态）。
- **不过就停下来调**（一次只动一个变量，最多 3 轮）：
  - 先换提示词改写（若弃答高）；
  - 再看事件筛选是否过严（若三条件都接近 50%）；
  - 再考虑换地图/换 seed（若该组 Alice 的 pre/post 分歧状态太少）。
- 每轮都留档；连续 3 轮不过则重写事件池（用户已允许推倒重来）。

### S2 正式复现（6 组）
- 每组 50 事件 × 3 条件 × 3 重复 = 450 次调用；6 组约 2700 次，按 10s/次 ≈ 7–8 小时（可切分多轮后台跑）。
- 冻结：事件划分、印象、提示词、模型、temperature=0 后不再按结果调整。
- 中途若某组出现系统性弃答（>50%）或设施/事件构造异常，**停止该组并留档**，不静默补齐。

### S3 提示词稳健性（1 组，同事件）
- 在 S2 某一组上，用 2 个改写版本各跑一遍（450×2 次调用）；
- 报告"新旧效应"在三个版本下的区间；若某版本效应消失或反转，如实报告（这正是 M17 目前最大的风险点）。

### S4 统计与结论
- 单组：McNemar 精确检验 + bootstrap CI；
- 汇总：先把每组算成 1 个效应量（group-level），再做跨组汇总（报告组间范围与随机效应均值，避免把同组事件当独立样本）；
- 报告三档结论：①多组一致正向 → 动机可作正式实验；②部分组正向、部分中性 → 写成"存在证据、受地图/seed 调制"；③整体无效应 → 回退到 M17 单组表述或重新设计（不硬报）。
- 可选（另开）：B 链得分实验——但**先要过 Oracle 门槛**（见下）。

## 3. B 链（得分）恢复的前提

M18-B 失败在控制器：Oracle 只有 +0.375 碗、p=0.35（开发集 v5 仅 +0.17）。所以：
- 不要直接在 M19 报得分；
- 先恢复 M17 时代的控制器（正确 vs 反向预测差 +1.15 碗），并在新事件上重建 **Oracle 门槛**：开发集 Oracle − 无预测 ≥ +0.5 碗且符号检验 p<0.05；
- 过门槛后再用新 checkpoint/事件跑得分续局（`m17_fixed_online_rollout.py` 已支持 checkpoint 参数）。

## 5. 防坑清单

- 用 conda `agentresume` 解释器（torch）；`.venv` 只用于纯离线分析。
- 每组一定要先验证 pre/post 在候选状态上确实分歧（PRE vs FETCH），否则该组直接判"无事件"，不要凑。
- 事件去重与"旧 pilot 永久排除"规则沿用 M17；跨组事件哈希去重（避免同局面被多组重复计）。
- 弃答必须单独报告；不要把弃答当答错后只报一个总准确率（M18 的教训）。
- 每次跑批都留 manifest（config hash、checkpoint hash、prompt hash、事件 hash），便于审计。
- 中途结果差就调整并留档，不覆盖旧结果（用户明确要求"不怕重来"）。
