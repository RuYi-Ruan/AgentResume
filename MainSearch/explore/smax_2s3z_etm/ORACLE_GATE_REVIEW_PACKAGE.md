## 1. 修复后的画像表（v2，归因已改为环境真实命中事件）

**v2 的指标含义（明确写出）**：`damage_per_len` 的伤害**包含过量伤害**（按各攻击者的原始命中伤害计入、不分摊）；
`focus_share` 要求**同一内部子步**内真实命中同一目标。因此 v1 → v2 的集火比全面下降
**不能全部归因于冷却误计** —— 至少有两处口径同时变化：① 命中门控（冷却/射程/存活）；② 时间口径由
"整个环境步 + 按指令筛选"变为"**同一子步 + 真实命中**"，后者更严格 ✓。
另外：累加器使用**当步**的 `live`（在其清零之前），因此**终止步已计入**伤害/命中/存活步/局长；
排除终止步的只是"副本 vs wrapper 状态"对比（wrapper 在终止步自动重置）✓。

**做法**：复用环境自身的子步链（`_world_step` + 同 key 调度 + `_kill_agents_touching_walls` /
`_update_dead_agents` / `_push_units_away`），在每个子步用 pre-state 复算命中
（射程 + 双方存活 + `i≠target` + **武器冷却 ≤ 0**），并**逐子步**用 `_world_step` 的返回值做账本校验：
`clamp(pre.health − Σ原始命中伤害, 0) == _world_step.health`（**在墙体死亡处理之前** ✓，过量伤害按原始值计入、不分摊 ✓）。

**我的独立核验**（`results/verify_local/attribution_verify.log`）：
- 自检（92.7 s）**PASS**：冷却反例 —— `ally_0`(冷却 0) 命中 13.0、`ally_1`(冷却 0.4) **被挡下 0.0**、`focused=0`、
  账本 `max|dev|=0.000e+00`；**去掉冷却门控的反向对照**凭空多出第二次命中 ⇒ 账本 `dev=13.0` **拒绝**该说法 ✓；
- 真实 rollout：96/96 子步账本精确；无门控对照 **71/96 失败**（max|dev| 26.0）✓；
- 全量：12 候选 × 20 局 = **142,888 次子步账本校验 + 17,628 次副本-vs-环境状态校验，0 mismatch**（max|dev| 0.0）✓；
- 我的第三次独立重测与 `profiles.json` **逐字节相同**（sha256 `3fdcbf1f…`）✓。

**v1 错得厉害的直接证据（注意口径）**：以 i3u1250 为例，该配置下**双方全部单位**合计下达攻击 45,656 次，
其中 39,404 次（**86.3%，全体单位口径**）被冷却门控挡下、3,597 次被射程/存活/自身挡下；
而 **1,416 次命中是"单个身份（i3）"的数据** ⇒ **两者分母口径不同，不得相除** ✓。
结论只需一句：v1 把大量并未开火的单位计入并平分伤害 ⇒ 总账平衡但分错人 ✓。

### `damage_taken` 核对结论（按要求先核对再下结论）

旧实现**确实受影响**：它用「整个环境步的血量差（含墙体、排除终止步）」并用「是否有人向我下达攻击指令」筛选
⇒ 与本次错误同类。同 20 局探针（全 u1250 队伍）：v1 `[2562,2454,2397,2625,2727]` vs v2 `[2470,2293,2466,2711,2842]`，

### 局限（如实列出）

1. 环境步层面的「副本 vs 环境状态」校验对无门控开关**不敏感**（该开关只改命中复算）；抓出它的是**子步账本**；
2. 账本**无法区分零伤害命中**（本环境不存在：所有攻击值 ≥ 5）；
3. `damage_taken` 探针只覆盖全 u1250 队伍的 20 局；
4. `focus_share` 的方向是**观测**而非预测；20 个固定局面仍**不是独立样本**。
