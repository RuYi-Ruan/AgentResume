# 设计需求：三人 Overcooked 地图（用于验证"队友能力信息是否影响协作决策"）

> 这份文本可直接粘贴给外部模型。末尾附上我们当前的方案与已测数据，供其批判或改进。

## 一、我们要验证的命题（一句话）

在一个**三人协作**的厨房任务里，直接告诉某位智能体"它的两位队友当前能力如何"，**会不会改变它的最优协作行为并提高团队产出**。

- 如果连"Oracle 能力信息"都提高不了团队收益 → 学习型队友模型（动态维护对伙伴的认知）在这个任务上不可能有价值，该任务不适合做该研究。
- 如果 Oracle 能提高 → 第二步再验证"过时认知 vs 当前认知"是否导致不同决策（这才是论文真正需要的环境性质）。

## 二、环境机制（现成实现，不能改规则）

网格厨房；可用对象：
`W` 墙、` ` 空地、`0-9` 食材堆、`P` 锅、`B` 盘堆、`X` 交付点、`R` 菜谱指示牌、`L` 按钮式菜谱牌、`A` 智能体起点。

- 动作：每智能体 6 个原子动作（右/下/左/上/停留/交互）。
- 一局步数：目前 400 步（**可建议调整**），超时自动重置。
- 烹饪：一锅 = 同种食材 3 份；装满后需 20 步煮熟；必须取**盘子**装盘后送到 `X`。
- 菜谱：从候选集合采样；仅当智能体站在 `R`/`L` 附近时可见（每次成功交付后可重采）。
- 观测：**局部视野**（半径 r → (2r+1)² 格 × 约 35–40 通道）。我们的策略是**小前馈 MLP（256×256），无 CNN/RNN**；半径 3 → 7×7×35 ≈ 1,715 维（实用上限；全可见到 8,645 维，不可用）。
- 奖励：正确交付 +20、错误 −20；形状奖励（放锅 3、开火 5、取菜 5、取盘 3），部分有门控条件（例如"手上盘数 < 非空锅数"才给取盘奖励）。
- 算力：CPU-only，一次训练 8–20M 环境步约 30–90 分钟；希望 3 个种子量级可负担。

## 三、地图需要同时满足的性质

**P1 单人不足以自给自足。** 量化指标（含转向代价的交互步数）：
`单人首锅步数 ≈ 3×2×d(食材堆,锅) + 2×d(锅,盘堆) + 2×d(盘堆,锅) + 20(煮) + d(锅,交付点)`
希望：单人 ≲1.5 份/局，而三人分工 ≥3 份/局。

**P2 能力差异会改变最优分工。** 需要存在大量"**同一厨房局面**，因队友能力不同（例如一个擅长取食材、一个擅长交付）而最优动作不同"的状态。

**P3 可学。** 三人 + 小前馈 MLP + 局部视野（半径约 3）+ 10–20M 环境步内能学出上升的出汤曲线。
注意：我们在小图上试过前馈 MLP，20M 步**零出汤、零形状奖励**；地图过大/过稀疏或视野过小都可能直接学不动。

**P4 无结构缺陷。** 三个起点之间全部可达（无被隔离的智能体）、没有单人绕近路完成全流程的捷径、不过度拥挤（每人至少十几个可走格）、队友行为在视野内可被观察到。

## 四、硬约束与取舍

- 只能用上面列出的对象与规则，不引入自定义机制（保持 benchmark 可比性）。
- 全可见观测维度爆炸（如 13×19×35 = 8,645 维）→ 只能用局部视野；半径 3 是经验上限。
- 锅是吞吐瓶颈：3 料/锅、20 步/锅；锅少则并行度低，锅多则任务变简单、单人也能刷。
- 每局 400 步可调（600/800 等）；如延长局时更容易同时满足 P1 与 P3，请直接建议。

## 六、我们当前的方案（供批判）

- 三人图，局部视野 3，**2 锅 + 1–2 盘堆 + 两个食材堆分置远角 + 交付点在对角**，三个起点分散 → 目的：让"走路成本"主导，拉开单人/三人差距。
- 已用静态检查器量化（含转向代价的 Dijkstra）：

| 候选地图 | 规模 | 可走格/人 | 单人独自出汤（400 步） |
| --- | --- | --- | --- |
| small | 13×9 | 23 | 3.96–4.65 份（单人自给自足，不合格） |
| mid | 19×13 | 59 | 2.76–3.74 份 |
| long | 25×15 | 97 | 2.34–2.86 份 |

- 计划：先用 2 人**全可见**图做"小前馈 MLP 能否学会"的单变量测试（验证训练管线），再上三人 mid/long 图。
- Oracle Gate 设计：同一次训练里**混合三档能力的冻结伙伴**（每局 0.00 / 3.04 / 11.54 份，取自我们训练到不同阶段的检查点），ego 分别"不知道/知道"伙伴档位；比较团队每局出汤数，判据 ≥ +1 份/局。
