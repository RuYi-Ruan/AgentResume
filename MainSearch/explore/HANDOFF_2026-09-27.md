## 一、研究目标与三道前提

研究主题：**ETM（Evolving Teammate Model）**——至少三名固定身份智能体持续协作、各自学习，并各自维护"对其他伙伴当前能力"的动态认知，用于改善协作决策。伙伴能力必须通过**协作经验逐步演化**，不能用切换 checkpoint 模拟成长。

主实验前需要满足三道前提（缺一不可）：

| 代号 | 含义 | 判据 |
| --- | --- | --- |
| **P1** | 单人自给自足不了 | 单人 320 步内出汤 ≲1.5 份 |
| **P2** | 伙伴能力随持续经验演化、且身份固定 | 同一 identity 的 early→late 能力/行为确有变化（独立 actor、连续 optimizer 轨迹） |
| **Oracle Gate** | "知道队友真实能力"能改变观察者的最优决策并提高团队收益 | Oracle − NoInfo 显著为正，且行为分布发生可解释变化 |

只有三道都过，才值得做 ETM 主实验（NoInfo / Frozen / Online / Oracle 四臂对照）。

### B. OvercookedV2 官方管线校准与"学不起来"的根因

- 跑通 JaxMARL v0.2.0 官方 CNN+GRU IPPO 管线（本地补两处 Flax 0.10 兼容）：**205 环境步/秒** ⇒ 3000 万步 ≈ 74 小时/种子 ✗ 本机不可行。
- 换成小前馈 MLP（256-256）后：**61 个检查点全部 0 出汤、0 形状奖励**（20M 步）。
- **根因（重要）**：V2 的形状奖励表里**没有"取食材"项**（只有放锅 3、开火 5、取盘 3、取菜 5，且取盘/放锅都有门控）⇒ 最早的奖励事件要求"手持正确物品 + 面朝正确物体"的合取，随机前馈策略撞不上 ⇒ **探索链断在第一环**（不是步数问题）。
- 附带结论：单人瓶颈在**策略网络**而非环境（环境 210k 步/秒、小 MLP+PPO 5.7k、CNN+GRU+PPO 998）。

### C. 三人三臂图（自定义地图）

- 设计 `three_arm_v2`（19×13、107 可走格）：左臂取料、中臂锅、右臂盘+交付、底部两行连通、三个固定起点；静态核验单人 320 步出汤 1.14–1.20 份 ✓（**P1 ✓**），脚本路线实测 234 步完成 1 份。
- 原版（外部给的 `three_arm`）有缺陷并保留为失败记录：第三个起点与盘堆堵死通往右臂的唯一通道。
- 关键机制（实测，别再猜）：V2 动作是**绝对方向移动**（一步内转身+前进；被挡只转身不计费）；`max_steps` 用 320；单一菜谱 `[0,0,0]`。

### D. 自举（BC）

- `generate_demos.py`：脚本专家、6 种角色排列、把队友当动态障碍、含扰动（随机起始延迟/2% 随机动作/停顿）⇒ 300 局中 **294 局有形状奖励、251 局成功交付**。
- **踩过一个大坑**：第一版演示把「动作 t」和「观测 t+1」配了对 ⇒ 离线指标虚高（0.989）但闭环全 0 ✗；修正后 BC 离线 macro 0.950、交互召回 1.00，**闭环采样 95.3% 局有形状奖励、68.8% 局出汤** ✓。
- 观测混叠诊断（决定是否需要记忆）：H(A|O) = 0.037 nats、多数动作占比 0.9898 ⇒ **前馈足够，不需要 GRU**（在该图上）。

### E. 单策略 PPO 的修复（CTDE critic）

- 现象：从零 PPO 学不动；且加入"保真协议"后一旦撤掉锚点就崩，熵上升、优势像噪声。
- **诊断**：局部视野 critic 的**解释方差 EV ≈ 0**（−0.52…+0.06）⇒ 优势是噪声。改为 **CTDE 紧凑 globals 状态（35 维）**做 critic 输入 + value normalization 后：EV 升到 **0.75–0.93**、优势方差降 ~50% ✓（Gate C0 通过）。
- 另修两处：训练奖励**漏了官方基线里的 shaped 项**（现补上，系数固定 1.0）；value 回归改 Huber。

### F. 独立 actor（P2 成立）

- `train_ocv2_independent.py`：三个 actor 各自 optimizer/梯度流 + 每个 agent 一个 CTDE critic。
- **致命 bug（外部审查发现，已修）**：`tx.update()` 返回的**已是参数更新量**，却又被送进 `TrainState.apply_gradients(grads=updates)` ⇒ **双重优化器**（Adam → Adam，符号可能翻转、两套 optimizer state 各自前进）。修复后：预热期正常、解冻不再崩、BC/ref-KL 损失不再爆。
- **修复后结果（P2 ✓）**：4.9M 步，团队出汤 **1.13 → 1.91 份/局**（+69%），且**自发分化**：agent2 交互占比 44–46%（服务者）、agent0/1 为 9–11%（取料者），两两策略 TV 0.70–0.79。
- 能力画像（`profile_capabilities.py`，按事件归因到身份）：早期三者"样样通"（0.35–0.72）→ 晚期 = 两名纯取料专家 + 一名锅/盘/交付专家 ⇒ 能力演化是学习产生的 ✓。

### G. Oracle Gate（三人图）

| 版本 | 伙伴 | 结果 |
| --- | --- | --- |
| 脚本角色原型（强/弱取料、强/弱服务） | 行为固定、绝不解锁第二角色 | 关键配对 **+0.62 / +0.59 / +0.97**（3 种子，t≈2.5–4.9）✓ 通过 |
| **学习型伙伴**（真实训练出的策略） | 角色从行为上可辨识 | **Δ = +0.01 / −0.02**（两次独立实验）✗ 冗余 |

⇒ 机制解释：**信息在"补偿不可观测"时有用，在"伙伴行为本身可辨识"时冗余**。

### H. 瓶颈相图、节流诊断与三次测量纠错（结论多次撤回，务必看时间线）

- 相图（B×C 3×3，ego 强制两种角色）曾显示"翻转格 +0.31"；节流诊断（同策略 1.0× vs 0.8×/2×）曾显示"2× 时 D 从 +0.31 翻到 −0.50"。
- **外部审查发现脚本 ego 与测量原语有三处 bug，修正后这些"翻转"全部消失**：
  1. `measure_throughput.py` 的 μ_I 把锅的任何位掩码变化都算成放锅（含 raw→cooking→cooked→被取走）⇒ 高估 64%；改为只统计 `ingredient_count +1`；
  2. `server_cycle` 测的是"首次交付延迟"（含 20 步煮制与上游生产），不是稳态服务循环；改为**两次"空手→持盘"之间**的单次干净循环；
  3. 脚本 ego/伙伴**不避让队友**（`blocked=frozenset()`）⇒ 在窄通道被堵、成绩被系统性压低；补齐"队友当障碍 + 卡住侧移"后，A 测试的 D 从 **+0.31 变成 −0.25**、2× 从 −0.50 变成 −1.12 ⇒ **符号翻转消失，"能力差→角色翻转"未获确认**。
- 教训：**测量口径必须先对齐再谈地图**；任何"翻转/提升"都要先排除拥堵与状态计数类 confound。

### I. B′：六张候选地图与窗口判据（Overcooked 的收束）

- 引入外部给的**吞吐窗口判据**：ρ = 3·μ_S^cap/μ_I 需落在 **0.8–1.0**（有 margin 时 0.82–0.98）。
- 实测六张图（v2、B1–B5）**全部 ρ ≈ 1.47–2.05** ✗ ⇒ 取料侧恒为更紧的瓶颈；原因是拓扑：一份汤要 3 趟取料 vs 1 个服务循环，且服务腿受地图尺寸限制（19×13 最长 ~55 步、25×15 ~67 步，而窗口需要 ≥85–107）。
- 想靠"增加并行取料者"抬高 μ_I：**Traffic Gate 失败**——并行效率 η_I = μ_I(2)/(2·μ_I(1)) = **0.50（B4）/ 0.636（B5）**，远低于 0.85 ⇒ 同角色伙伴在通道里互相堵死。
- ⇒ **按事前写死的停止规则**：Overcooked 停止再造地图，保留为**负控制环境**（能力会演化 ✓、行为会分化 ✓，但 ∂a*/∂c ≈ 0 ⇒ ETM 不应有收益）。研究决策记录见 `overcooked_v2_3p_gate/RESULTS.md §14`。

### J. RWARE（校准用，已归档）

- 4 智能体 tiny-4ag：共享参数 IPPO 与独立 IPPO 都学得动（20.48M 步 ⇒ 采样 14.09 份/局）。
- Oracle 门槛（冻结伙伴三档 + 观察者被告知档位）：**未通过**（Δ = +0.23 ± 0.30）。
- ETM 接口六臂对照（none/frozen/online/onehot/aux/visible）：**没有任何一条超过对照**。
- 结论：RWARE 属"伙伴能力差异真实、但动态认知对决策不重要"的环境 ⇒ 只作测试校准。

### K. SMAX（当前主线）

- **A 轮（已跑完，但因实现 bug 而无效 ✗）**：自定义 FF MLP 在 `3m` 上，LR 1e-3 + 线性退火，10.24M 步（19.4 分钟）⇒ 训练胜率 0.000、采样评测胜率 0.000、贪心胜率从第 1 段起固定 0.090 且全程不动。
  - **失效原因（外部审查发现，重要）**：退火的 `transition_steps` 传的是 PPO **更新次数**，而 optax schedule 数的是**优化器步数**；每轮 4 epochs × 4 minibatches = 16 步 ⇒ 学习率在 **update 156 ≈ 64 万环境步**就归零（预算本是 1024 万步）⇒ 平线不可归因于网络形态。修复采取**官方公式**：`frac = 1 − (count // (minibatches × epochs)) / total_updates`（`count` = 优化器步数，整除）。另一处细微差别已记录：`optax.linear_schedule` 与官方公式**时间尺度相同但不严格等价**（前者每个优化器更新都微降，后者每个 PPO 更新内恒定）。
  - ⇒ **A 轮作废为"无效"**，不作为"前馈学不起来"的证据，按外部指示不重跑；迁移官方 RNN backbone 的结论由 B 轮单独支撑。
- **B 轮（✓ 已判定）**：官方 `ippo_rnn_smax.py` 原生 `2s3z`（GRU-128、LR 4e-3、ANNEAL_LR、128 环境 × 128 步 × 10M 步），实测吞吐 **~1,140 步/秒**。曲线：step 16,384 win 0.000 ret 0.201 → 212,992 win 0.000 ret 0.378 → 753,664 win 0.000 ret 0.671 → **1,720,320 win 0.562 ret 1.508 → 1,818,624 win 0.685 ret 1.654**（熵 1.31 → 1.12）⇒ **约 1.7–1.8M 步开胡** ✓ 训练链正常。
- 分流结论：**A（无效）+ B✓ ⇒ 迁移官方 RNN PPO backbone**；`3m` 只完成训练器自检，不再调参。
- 附带修正：**评测胜率统一改用环境原生 `returned_won_episode`**（旧的 `step_reward>=1.0` 作废，因为 SMAX 奖励含伤害/击杀等 shaped 分量）；custom 侧新增 `--anneal-lr`。归档的"贪心胜率 0.38/0.21"**作废为未验证旧结果**。

### 结构性（决定了 Overcooked 的命运，不是 bug）

- 三臂图**取料恒为瓶颈**（ρ 1.47–2.05，需 0.8–1.0）；服务腿受地图尺寸限制；增加并行取料者被交通封顶（η_I ≤ 0.636）；
- 自然训练的同角色能力差**只有 1.25×**（放锅/步 0.0128→0.0160，且非单调）；
- 因此"能力大小"不改变最优角色 ⇒ 学习型伙伴下能力信息冗余（Δ≈0，两次独立验证）。

### 未解 / 待观察

- **SMAX `3m` 上前馈策略学不起来**（A✗）：指向部分可观测性（需要 recurrent policy）；
- **`2s3z` 的胜率尚未脱离 0**（~21 万步）：待 B 轮推进（预期百万步级开胡）；
- **算力约束**：官方 GRU 约 930 步/秒 ⇒ 主实验若用官方 backbone，8 臂 × 10M 步 ≈ 8–10 小时/轮（可接受但偏紧）；FF 底座快 10 倍但学不起来。

- Jumanji RWARE 与 JaxMARL 的 `reset` 返回约定不同（`(state, timestep)` vs `(obs, state)`）。
